# No Code Comments (Except `.env`)

This rule enforces the project-wide convention defined in `AGENTS.md` (§ Language > Comments).

---

## Rule

**NEVER** add inline comments (`// ...`) or block comments (`/* ... */`) to source code.

Code MUST be self-documenting through clear naming conventions, well-named methods, and intentional code structure — **not** through comments.

---

## Allowed Exceptions

### 1. `.env` and `.env.example` Files
Comments **ARE ALLOWED** and **RECOMMENDED** to document configuration variables.

Example:

```env
# Maximum number of database connections in the pool
DB_POOL_SIZE=10

# Time-to-live for OTP codes, in seconds (5 minutes)
OTP_TTL_SECONDS=300
```

### 2. Javadoc (Java) and JSDoc (TypeScript)
Only allowed for **public APIs** when the documentation provides information that **cannot** be inferred from the signature alone:

- **ALLOWED**: `@return client IP address, or "Unknown" when invoked outside an HTTP request scope`
- **ALLOWED**: `@throws IllegalArgumentException if the input is null`
- **FORBIDDEN**: `@return the IP` (just restates the method name)
- **FORBIDDEN**: `@param request the request` (just restates the parameter name)

Javadoc/JSDoc must be **terse** and add **real value** beyond what the code already expresses.

---

## Forbidden Comment Types

The following comment patterns are **strictly forbidden**:

| Pattern | Reason |
|---------|--------|
| `// This method does X...` | Restates what the method name already conveys |
| `/* Handle edge case */` | Use a well-named helper method instead |
| `// TODO:` or `// FIXME:` | Use the issue tracker, not source comments |
| `// HACK:` or `// XXX:` | Refactor properly; do not leave warnings in code |
| `// ==== SECTION ====` | Use package/private class organization instead |
| `// <copyright>` headers | Configure the build tool / license plugin instead |
| `// Generated by...` | Configure the generator's header option instead |
| License headers at top of file | Configure in build tool / formatter |

## How to Write Self-Documenting Code Instead

### Bad (commented)

```java
// Calculate total price with tax
public double calculate(double price, double taxRate) {
    // Apply tax to price
    double taxed = price * taxRate;
    // Add tax to original price
    return price + taxed;  // Return total
}
```

### Good (self-documenting)

```java
public double calculateTotalWithTax(double price, double taxRate) {
    double taxAmount = price * taxRate;
    return price + taxAmount;
}
```

### Bad (explaining magic numbers)

```java
// 86400000 = milliseconds in a day
long dayInMs = 86400000L;
```

### Good (named constant)

```java
private static final long MILLIS_PER_DAY = 86_400_000L;
```

### Bad (section dividers)

```java
// =================== UTILS ===================
public class StringUtils { ... }
// =============================================
```

### Good (organized packages)

```
com.pwb.backend.shared/
├── string/
│   ├── StringNormalizer.java
│   └── StringValidator.java
```

---

## Enforcement Checklist

Before writing or submitting code, verify:

- [ ] No `//` or `/* */` comments in source files (except `.env`/`.env.example`)
- [ ] No `TODO`, `FIXME`, `HACK`, `XXX` markers anywhere in code
- [ ] No section divider comments
- [ ] No redundant Javadoc/JSDoc that just restates the signature
- [ ] All public APIs that need documentation have concise, value-adding Javadoc/JSDoc only
- [ ] All variables, methods, classes use clear, descriptive English names
